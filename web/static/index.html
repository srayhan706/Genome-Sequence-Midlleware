Workbench

Smith–Waterman local alignment. The middleware hands the job to the next idle worker over MPI; large inputs are filled as a tiled anti-diagonal wavefront with OpenMP.

KMP exact-match search. Texts over 1 Mbp are split into chunks of start positions searched in parallel with OpenMP.

Counts every length-k substring. K-mers are packed 2 bits per base into a 64-bit integer that slides along the sequence; large inputs are split across OpenMP threads.

One RPC, many alignments. The middleware runs one dispatch thread per worker so every worker is busy at once (scatter), then returns the results in order (gather). Compare wall time to the sum of compute time.

A simulated sequencer: reads arrive in chunks and each chunk is sent for k-mer counting as soon as it is produced. Totals update in near real time; watch the cluster panel to see chunks land on different workers.

Fires many requests at once with unique random inputs (so nothing comes from the cache). The timeline shows each request as a bar on the worker that computed it — overlapping bars on different rows are jobs running in parallel on different MPI ranks.

How a request flows through the system
  1. The browser posts JSON to the gateway, which calls the middleware over gRPC.
  2. The coordinator (MPI rank 0) validates the input and checks its LRU cache; a hit is answered immediately.
  3. Otherwise the dispatcher takes the next idle worker from a pool and sends it one framed MPI message (task type + packed parameters).
  4. The worker runs the algorithm (using OpenMP threads for large inputs) and replies with the packed result and its compute time.
  5. The coordinator caches the result and answers the gRPC call. Different gRPC threads use different workers at the same time (MPI_THREAD_MULTIPLE).
